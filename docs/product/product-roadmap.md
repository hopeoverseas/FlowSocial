必须独立确认后才能考虑重新授权调用。离线合同回归、真实 Provider 质量、真实平台闭环分别验收。

本次优先推进合成夹具/隔离回归、静态与费用入口边界、文档一致性、GitHub/CI 准备及真实业务验收输入。
工程状态只写 [PROGRESS.md](../PROGRESS.md)，可执行 P0/P1/P2 任务写 [NEXT_STEPS.md](../NEXT_STEPS.md)，
真实业务验收输入写[验收清单](../operations/business-acceptance.md)，不在历史正文重复登记本次执行状态。
团队公网部署、认证/RBAC、并发隔离和自动发布需独立设计，当前不能直接当作生产 SaaS。

本规划用于统一 FlowSocial 后续迭代方向，解决多条任务线分别开发后出现的流程、字段、状态和完成度不一致问题。它不是一份短期待办清单，而是后续判断功能是否应进入主链、是否可以上线、是否需要调整契约的总参考。

项目需要同时达成两个目标：

1. 先形成一条可以从策略诊断运行到内容生成、人工发布和反馈复盘的完整 V1 主链；
2. 让策略、内容、热点、爆款、标题、视觉和反馈能力能够通过版本化 Skill、规则库和评测集持续优化，而不必反复推翻系统主流程。

本规划的核心决策是：

> 先建设“薄而完整、状态稳定、全程可追溯”的 V1，而不是继续横向堆叠局部完成的高级能力。V1 可以在建议质量和自动化程度上粗糙，但不能在状态、数据、版本、归因和用户确认机制上粗糙。

## 2. 产品目标与 V1 定位

### 2.1 长期产品目标

FlowSocial 的本质是一个社媒垂类 Agent，而不是一组热点、选题和文案工具。它应当能够：

- 通过对话理解用户的商业模式、产品、受众、账号目标、资源和限制；
- 为不同阶段的用户形成账号定位、增长打法和运营计划；
- 按需要调用热点、知识库、爆款蓝图、标题、写作、自然化、视觉和审核能力；
- 陪伴用户完成方向选择、大纲确认、内容生成、修改、发布和复盘；
- 在持续发布中沉淀账号经验、表达偏好和有效内容模式；
- 将内容层观察与长期策略调整严格分层，避免因单篇内容自动改变账号定位。

### 2.2 V1 产品定位

V1 不是最终成熟的自主社媒运营 Agent。V1 的目标是证明以下闭环可以稳定运行：

```text
创建公司与社媒账号
→ 可选上传业务资料
→ 策略 Agent 完成最低可用诊断
→ 生成并激活粗版策略
→ Agent 推荐内容方向
→ 用户确认方向和大纲
→ 生成小红书或公众号内容包
→ 用户修改并下载
→ 用户人工发布
→ 记录发布和基础数据
→ Agent 给出内容复盘及下一篇建议
```

V1 首先服务单公司、一个主要运营账号的黄金路径。底层继续保留矩阵、多账号和多打法模型，但复杂矩阵协同不作为 V1 主链的前置条件。

## 3. 总体设计原则

### 3.1 确定性系统负责“不乱”

以下能力必须由确定性代码、契约和状态机控制：

- 当前处于哪个阶段；
- 当前正在处理哪个字段或任务；
- 哪些问题已经问过、回答、跳过或失效；
- 哪些信息是事实、用户偏好、假设、建议或冲突；
- 是否满足生成草案、生成正文和发布记录的门槛；
- 策略、事实、内容、Skill、发布和表现数据的版本关系；
- 用户确认、回退、重试和失败恢复；
- 安全、授权、事实和风险边界。

### 3.2 LLM 与 Skill 负责“越来越聪明”

以下能力可以持续替换和优化：

- 策略诊断和商业建议；
- 问题的自然语言表达；
- 增长打法推荐；
- 内容方向和来源评分；
- 爆款拆解；
- 大纲、标题、正文、自然化和视觉；
- 反馈诊断和实验建议。

LLM 不得自行决定系统阶段、完成状态、长期数据写入、用户确认结果或活动策略变更。

### 3.3 先冻结骨架，再迭代智能

应保持稳定的主对象链：

```text
StrategySession
→ StrategyDraft
→ ActiveStrategySnapshot
→ RollingContentPlan / ContentOpportunity
→ ContentRun
→ ContentTask
→ PublicationRecord
→ PerformanceSnapshot
→ FeedbackAction
→ StrategyReviewCase
```

可替换能力只能通过版本化输入输出合同与这些对象协作，不得建立平行状态。

### 3.4 用户确认优先

- 用户明确回答高于历史推断；
- 用户本篇内容选择高于 Planner 默认建议；
- 用户可以覆盖内容目的、主题和来源方式，但不能绕过事实与风险门禁；
- 长期策略调整必须经过策略 Agent 复核和用户确认；
- 单篇表现不得自动改写活动策略。

### 3.5 所有结果必须可追溯

每个关键输出至少能追溯到：

- 所用策略和事实版本；
- 所属公司与社媒账号；
- 使用的增长打法和实验；
- 内容来源快照；
- Skill 与模型版本；
- 用户修改和确认；
- 最终发布版本；
- 发布后表现数据。

## 4. 当前项目基线判断

截至本次接手，源码具备策略激活、周期计划、平台大纲、原子生产、人工审阅、本地交付、人工发布/反馈
事实和下一周期能力。修复前基线累计验证 42/43，轻结构改单夹具失败；最终工程验证只以 PROGRESS 的
命令结果为准。实现能力、本地合同、真实 Provider 与真实平台验收不能互相替代。

### 4.1 交接源码中已具备的能力

- Company → AccountMatrix → SocialAccount → EffectiveAccountStrategy 的稳定归属关系；
- 策略 Agent 的事实治理、对话诊断、建议讨论、版本化草案、激活和回退；
- 发布周期与多平台内容计划，以及在单个选题内通过 AI 对话讨论、确认调整方向；
- 数据反馈在周期完成后生成一批新选题，而不是只修改旧文章标题；
- 热点、知识库、爆款蓝图和用户素材的可追溯来源组合；
- 小红书与公众号按平台隔离的大纲合同、恢复请求和原子内容生产；
- 标题、正文、自然化、视觉、平台审核与质量 Gate；
- 不可变内容版本、局部修订、恢复、人工审阅、精确选择和本地交付包；
- 人工发布记录、CSV 数据导入、表现快照、漏斗诊断、战术实验与策略复核候选；
- “策略 Agent、今日陪伴、内容计划、内容生产、发布与复盘、资产中心、账号与设置”工作台；
- 关键状态检查点与显式恢复路径，模型合同失败不会静默写入错误平台对象；
- 历史 `ContentRun` 旧写入和只读路由已退役并返回 410，历史数据保持不可变。

### 4.2 当前主要问题

- `server.mjs` 与 `app.js` 仍是较大的聚合入口，跨模块修改的回归半径偏大；
- 对接其他存量数据时必须先确认旧记录范围和迁移责任，不能假设源码 seed 恢复原业务数据；
- 部分能力仍由 Feature Flag 控制，代码存在不代表默认产品入口已开放；
- 公众号真实资源上传受 `WECHAT_40164` IP 白名单阻断，真实草稿与发布不得据此宣称完成；
- 小红书视觉生成依赖外部 Provider，当前主链采用人工整套视觉确认；离线测试不证明真实图片质量；
- 当前 SQLite 与单工作区运行模型不适合多租户高并发生产环境；
- Provider、平台权限、真实发布效果和反馈对账仍需要在每次外部动作前经过人工门禁；
- 路线图后续章节保留了最初 V1 设计背景，其中的 `RollingContentPlan`、`ContentRun` 与
  `ContentTask` 仅用于说明历史模型；当前写入主链以系统架构第 1–4 节为准。

## 5. V1 黄金路径（历史方案）

### 5.1 用户主流程

```text
1. 创建公司
2. 创建或选择一个主要社媒账号
3. 可选上传产品、案例、SOP 或公司资料
4. 启动策略诊断
5. 完成最低必需信息
6. 确认一个主要增长打法
7. 生成 MinimumViableStrategy 草案
8. 用户修改或确认并激活
9. 生成未来 7 天或下一篇内容方向
10. 用户选择推荐方向或输入临时主题
11. 系统解析知识、热点、蓝图和临时素材
12. 构建 ContentMaster
13. 生成大纲并等待用户确认
14. 生成平台正文、标题和内容包
15. 用户局部修改并完成质量检查
16. 下载内容包
17. 用户人工发布
18. 记录发布、采用情况和 URL
19. 在 72 小时或 7 日录入基础数据
20. 生成内容诊断和下一篇实验建议
```

### 5.2 V1 稳定启用能力

- 单账号策略诊断；
- 一个主要增长打法和一个备选打法；
- 最低可用策略草案；
- 活动策略版本；
- 知识库上传、解析和检索；
- 单账号内容推荐；
- 7 天滚动计划；
- 知识库生成；
- 热点 + 知识库生成；
- 用户临时素材生成；
- 方向卡、大纲确认和正文；
- 小红书/公众号平台适配；
- 标题、基础审核和局部修改；
- 小红书内容包、公众号 HTML/Markdown 下载；
- 人工发布记录；
- 人工或 CSV 数据回填；
- 单篇诊断和下一篇战术建议。

### 5.3 V1 暂不作为主链前置能力

- 复杂多账号矩阵自动规划；
- 多账号同题自动协同生成；
- 全自动热点打法切换；
- 自动改变长期策略；
- Skill 自动晋升并立即影响生产；
- 公众号自动发布；
- 小红书自动发布；
- 小红书官方数据自动同步；
- 复杂跨周期因果判断；
- 多成员审批流；
- SaaS 级租户与权限体系。

这些能力保留代码和数据接口，通过 testing、experimental 或 disabled 状态隔离，不得阻断 V1 黄金路径。

## 6. 策略 Agent V1 稳定化设计

### 6.1 唯一状态机

策略会话使用唯一阶段：

```text
not_started
→ core_diagnosis
→ core_ready
→ optional_enrichment
→ strategy_decision
→ draft_ready
→ draft_generated
→ active
```

任何模块不得自行发明并写入另一套会话阶段。Question Planner、Enrichment Planner、LLM 和前端只能消费权威状态机结果。

### 6.2 单轮处理顺序

```text
读取当前 StrategySessionState
→ 解析用户本轮输入
→ 更新 Claim / Fact / Conflict
→ 重新计算字段覆盖
→ 关闭已回答问题
→ 计算唯一 nextAction
→ LLM 组织自然语言回复
→ 保存完整 turn trace
```

LLM 不能自行选择目标字段或决定是否生成草案。

### 6.3 问题账本

每次问题至少保存：

```text
questionId
targetFieldPath
targetSlot
questionHash
reason
askedAt
answeredAt
status
sourceRevision
```

状态包括：

- pending；
- answered；
- partially_answered；
- skipped_slot；
- skipped_field；
- superseded；
- invalidated_by_new_fact。

相同字段、相同缺口、相同上下文版本的问题不能重复询问。只有旧答案失效、发生冲突或用户主动要求重谈时才能重新打开。

### 6.4 信息分级

九项策略骨架继续保留，但每项内部槽位分成：

1. `required_for_minimum_draft`：生成最低可用草案必须具备；
2. `recommended_for_quality`：缺失时允许以假设或待补充项进入草案；
3. `operational_learning`：通过后续内容与反馈逐步积累。

动态事实默认不阻断最低可用草案，除非涉及事实授权、法律风险或用户明确要求的业务约束。

### 6.5 MinimumViableStrategy

当最低必需字段完成后，即使部分高质量信息缺失，也允许生成：

```text
confirmedStrategy
confirmedFacts
explicitAssumptions
unresolvedQuestions
riskWarnings
recommendedNextEvidence
```

假设必须显式标识，不能伪装为用户确认事实。用户可以在草案界面继续修改和补充。

### 6.6 草案阻断解释

草案按钮不得无解释地禁用。系统必须返回：

```text
canGenerateMinimumDraft
canGenerateHighConfidenceDraft
blockingItems
qualityWarnings
availableActions
```

可选行动至少包括：继续回答、让 Agent 提供候选、跳过可选槽位、以假设先生成草案。

### 6.7 策略失败会话回放

所有真实失败对话应脱敏保存为回归案例，并自动检查：

- 是否重复提问；
- 是否跳错阶段；
- 是否遗忘用户确认信息；
- 是否把建议当事实；
- 是否错误关闭未完成字段；
- 达到最低条件后能否生成草案；
- 增长打法确认后能否激活策略。

## 7. 多账号矩阵与多打法安排

### 7.1 矩阵能力的处理原则

多账号矩阵不是删除，而是延后进入默认主链。

V1 继续保留：

- Company → AccountMatrix → SocialAccount 数据结构；
- 公司、矩阵、账号三级策略版本；
- EffectiveAccountStrategy 解析；
- 每个账号独立的增长打法、内容和反馈归因。

V1 默认体验：

- 用户指定一个主要运营账号；
- 策略 Agent 首先保证该账号形成完整闭环；
- 其他账号可以存在，但不自动进入复杂协同计划。

后续开放顺序：

```text
V1：单账号 + 多打法
V1.1：同公司多账号独立运营
V1.2：企业号/创始人号/专家号角色矩阵
V2：矩阵级动态复盘和分工调整
```

### 7.2 V1 增长打法

V1 保留多策略选择，但每个账号每个策略周期只确认一个主要打法。

最低支持：

1. 稳定垂直模式；
2. 热点桥接模式；
3. 受控热点实验；
4. 公众号权威/搜索内容资产模式；
5. 稳定账号内容组合优化。

策略 Agent 推荐一个主要打法和一个备选，解释适用条件、资源要求、风险、观察窗口和退出条件，最终由用户确认。

## 8. 热点冷启动 V1 设计

热点冷启动保留为产品差异化能力，但采用受控机制。

### 8.1 热点相关性等级

- `direct`：与业务、受众和内容支柱直接相关；
- `bridge`：可以通过真实业务问题自然桥接；
- `weak_experiment`：弱相关，只能经用户明确确认进入小规模实验；
- `unrelated`：完全无关，禁止自动推荐。

### 8.2 受控热点实验字段

```text
growthPlaybookId
experimentPlanId
hypothesis
maximumHotspotRatio
allowedRelevanceTiers
observationWindowDays
primarySignals
audienceDriftSignals
exitConditions
```

### 8.3 V1 禁止行为

- 完全无关热点自动进入计划；
- Agent 自主提高热点占比；
- 因单篇高播放自动改变账号定位；
- 自动删除历史垂直内容；
- 刷量、批量低质发布或伪造互动；
- 将热点事实和用户业务事实混为一体。

### 8.4 热点库

热点进入统一资产库，至少保存：

- 来源 URL 和采集时间；
- 原始标题和摘要；
- 相关性等级与理由；
- 时效和生命周期；
- 使用过的 ContentRun/Publication；
- 风险和人工审核结果；
- 是否已经用于同一账号。

## 9. 策略到内容的稳定边界

内容 Agent 不直接读取策略对话、策略 Agent 内部字段状态或提示词。所有策略变化通过 Adapter 投影到稳定合同。

### 9.1 ContentStrategyProfile

建议稳定包含：

```text
strategySnapshotId
strategyDecisionRevision
effectiveStrategyId
companyId
socialAccountId
accountStage
accountIdentity
targetAudiences
objectives
contentPillars
contentFunctionPolicy
platformRole
growthPlaybook
hotspotPolicy
evidencePolicy
riskPolicy
experimentPlan
```

策略 Agent 内部九项字段和动态事实以后可以变化，原则上只修改 Strategy Adapter。

### 9.2 所有内容入口统一归因

无论内容来自滚动计划、Agent 推荐、热点、爆款、知识库还是用户临时主题，都必须创建 ContentRun，并保存：

```text
strategySnapshotId
strategyDecisionRevision
strategyDecisionHash
factSnapshotId
effectiveStrategyId
growthPlaybookId
growthPlaybookVersion
experimentPlanId
validationHypothesis
primarySignals
exitConditions
```

不得只在滚动计划入口保存增长打法信息。

## 10. 内容 Agent V1 主链

### 10.1 规划阶段

内容 Agent 综合：

- 活动策略；
- 当前社媒账号身份；
- 增长打法和实验；
- 内容支柱覆盖；
- 最近内容历史；
- 热点库；
- 知识库；
- 爆款蓝图；
- 用户本轮请求。

第一版可以使用确定性规则评分，不需要复杂自主规划。每次返回 2–5 张方向卡，说明为什么推荐、使用什么来源、缺少什么事实和可能的重复风险。

### 10.2 ContentRun 状态机

```text
direction_selected
→ source_resolution
→ outline_drafting
→ outline_ready
→ outline_confirmed
→ generating
→ content_ready / needs_review / blocked
→ delivery_ready
→ publication_pending
→ feedback_pending
```

大纲未确认不得生成正文。缺少必需事实或证据时必须阻断或追问，不得依赖写作 Skill 自动补造。

### 10.3 平台内容链

小红书：

```text
ContentMaster
→ 大纲确认
→ 小红书正文和卡片
→ 可选自然化
→ 最终标题
→ 标题与事实 Gate
→ 视觉导演方案与逐页无字底图说明
→ 用户确认模型质量、候选数和预计调用量
→ Kie.ai 候选底图生成与逐页选择
→ 渲染
→ 真实图片视觉审核
→ 内容包
```

小红书视觉支持 `all_ai_backgrounds`、`smart_hybrid` 和 `deterministic_only` 三种模式。推荐模式允许每页都调用图片服务，但图片模型只负责无字视觉底图，中文标题和正文始终由确定性排版层叠加。VI、PPT/PDF 和参考图先进入授权资料与 Design DNA 快照；provider 不支持参考图输入时，只使用用户批准的文字化视觉摘要。任何付费生图调用前都必须展示并确认 provider、model、quality、逐页候选数和预计调用总数；失败页只能显式重试、换候选或逐页回退，不得静默将整套切回 HTML/CSS。

整页含中文生成继续作为 `experimental` 方向，不替代上述 V1 稳定路径。2026-08-03 的 05E 真实对比中，两个挑战模型均未同时满足精确 1080×1440、稳定中文和参考隔离门槛。因此必须分别保存 Provider 原始尺寸状态、确定性规范化状态和最终画布状态；后处理达到 1080×1440 不得改写为 Provider 原生尺寸通过。只有规范化后重新通过 OCR、事实、视觉和人工选择，且单测试账号 Feature Flag 明确开放时，整页模式才能进入灰度；在此之前新任务默认继续使用确定性中文排版。

公众号：

```text
ContentMaster
→ 大纲确认
→ 公众号文章
→ 内容审核
→ 可选自然化
→ 最终标题
→ 标题与事实 Gate
→ 配图计划
→ HTML 格式化和校验
→ 内容包
```

### 10.4 修改与版本

- 文案、标题、图片规格等局部变化使用结构化 Patch；
- 事实、案例、主题、内容目的和推广方式变化重新建立上游 Run；
- 任何修改都生成版本或明确的待确认状态；
- 已发布版本不可被后续编辑覆盖；
- 发布反馈必须绑定实际发布的内容版本。

## 11. 知识库与资产中心

### 11.1 四类资产分离

1. 企业知识：产品、案例、数据、SOP、FAQ 和品牌资料；
2. 热点资产：外部事件、来源、时效和风险；
3. 外部参考：原帖、文章、视频转录、截图、指标和授权；
4. 爆款蓝图：从参考内容提取的标题、开头、结构、视觉和互动机制。

### 11.2 事实边界

- 企业知识可以提供用户业务事实，但必须记录来源和公开权限；
- 热点可以提供外部事件事实，但必须保留来源和时效；
- 用户临时文字可以作为本次内容事实，但默认不自动升级为长期策略事实；
- 爆款蓝图只能提供创作机制，不能提供用户业务事实；
- 未完成 OCR 或转录的图片/视频只能作为素材，不能作为确定事实。

### 11.3 V1 知识库目标

- 上传、解析、检索和引用稳定；
- 策略诊断可按当前缺口读取资料；
- 内容生成可冻结 KnowledgeSnapshot；
- 用户能看到资料是否被使用；
- 资料冲突、权限不明和过期时要求人工确认。

## 12. 发布与反馈闭环

### 12.1 V1 发布方式

小红书：

- 下载内容包；
- 用户人工发布；
- 记录平台 URL、发布时间、是否采用和修改摘要；
- 手工或批量导入数据。

公众号：

- V1 输出 Markdown、可粘贴 HTML 和预览；
- 用户人工放入公众号后台发布；
- 后续增加草稿箱同步和 FlowSocial 定时任务；
- 群发推送与自动发布属于更高风险能力，不作为 V1 必需项。

### 12.2 PublicationRecord

必须包含：

```text
publicationId
platform
platformContentId
url
publishedAt
contentTaskId
contentVersion
contentRunId
companyId
socialAccountId
strategySnapshotId
effectiveStrategyId
growthPlaybookId
experimentPlanId
sourceSnapshotIds
skillExecutionRecordIds
```

同一平台内容 ID 或同一内容任务版本不得重复创建发布记录。

### 12.3 表现快照

- 缺失指标保持 `null`，不能当作 0；
- 72h、7d、final 分开保存；
- 修改数据产生新修订，不覆盖历史快照；
- 平台指标和业务结果分开；
- 每个派生比率必须保存分子、分母和指标字典版本。

### 12.4 内容战术闭环

```text
PerformanceSnapshot
→ FunnelDiagnosis
→ 用户采用 OptimizationAction
→ 注入指定的下一篇或未来若干篇
→ 到达观察窗口
→ supported / partially_supported / rejected / insufficient
→ 停止或继续实验
```

OptimizationAction 必须限定：

- 社媒账号；
- 平台；
- 内容职能/支柱；
- 只改变一个主要变量；
- 保持不变的条件；
- 目标指标；
- 有效期和验证窗口。

### 12.5 策略反馈闭环

策略上行必须使用持久化 StrategyReviewCase：

```text
跨周期可比样本
→ 重复模式和业务结果
→ StrategyReviewCase
→ 策略 Agent 审核
→ 接受 / 拒绝 / 追问 / 继续观察
→ 用户确认
→ 新 StrategyDocument
→ 新活动策略版本
→ 新一轮内容验证
```

单篇内容只能影响内容层实验。策略复核门槛至少要求多篇、多个真实周期、重复模式和一定业务结果，不得自动应用。

## 13. Skill 与业务逻辑持续优化机制

### 13.1 SkillDefinition

每个可优化能力至少包含：

```text
skillName
version
inputContract
outputContract
promptAndRules
referenceCases
evaluationDataset
qualityThreshold
failurePolicy
rolloutStatus
```

### 13.2 生命周期

- `development`：开发中，不进入运行主链；
- `testing`：内部可选使用；
- `experimental`：小范围灰度；
- `stable`：V1 默认主链；
- `deprecated`：不再创建新记录，保留兼容；
- `retired`：仅用于读取历史。

Skill 存在于代码库不代表已经进入生产主链。Feature Flag、Manifest 和前端状态必须一致。

### 13.3 升级流程

```text
发现真实问题
→ 保存脱敏失败案例
→ 加入评测集
→ 修改 Skill/规则/Playbook
→ 新旧版本回放对比
→ 合同与安全回归
→ testing
→ experimental
→ 观察用户修改和发布结果
→ stable 或 rollback
```

任何 Skill 不得根据少量内容表现直接改写自身生产规则。系统只能生成 Skill/Playbook 优化候选，必须人工审核和版本发布。

### 13.4 可配置业务逻辑

以下内容应逐步从散落代码中收口为版本化配置：

- 策略问题政策；
- 字段最低覆盖要求；
- 增长打法卡；
- 热点相关性和占比政策；
- 内容职能目标范围；
- 平台写作和审核规则；
- 反馈基线、样本门槛和退出条件。

安全、数据一致性、状态机和确认门禁继续由代码控制，不能全部配置化。

## 14. 评测体系

### 14.1 策略 Agent 评测

至少覆盖：

- 用户完全没有起号经验；
- 用户目标和商业模式表达模糊；
- 用户中途纠正之前的信息；
- 用户跳过某个问题；
- 用户上传资料与对话冲突；
- 用户要求 Agent 给候选建议；
- 已回答问题不得重复；
- 信息不足时明确显示缺口；
- 达到最低条件后一定能生成草案；
- 策略决策确认后可以激活；
- 新事实只使相关草案或决定过期。

核心指标：

- 重复提问率；
- 无效追问率；
- 草案成功率；
- 平均完成轮数；
- 用户修改字段数；
- 假设误写为事实的数量；
- 阶段跳转错误数。

### 14.2 内容 Agent 评测

- 同一主题在不同策略下方向明显不同；
- 缺少案例时不编造案例；
- 小红书和公众号不是简单改格式；
- 热点不能压过业务相关性；
- 标题与正文承诺一致；
- 内容来源与事实引用可追溯；
- 局部修改不破坏锁定事实；
- 上游变化重新经过大纲确认；
- 同账号重复主题被识别。

核心指标：

- 用户采用率；
- 用户修改率和修改范围；
- 事实错误数；
- 质量 Gate 失败率；
- Skill 降级率；
- 内容生成成功率；
- 从方向到交付的完成率。

### 14.3 反馈评测

- 未填写指标不等于 0；
- 72h 和 7d 不混算；
- 数据绑定正确内容和版本；
- 不同账号数据不混合；
- 单篇异常不触发策略修改；
- 优化行动只进入规定内容；
- 到期后行动能结束；
- 策略候选必须满足样本和周期门槛。

## 15. 实施优先级

### P0：V1 主链阻断项

目标：让一个真实用户稳定从策略走到反馈。

1. 修复策略决策激活的 `ready/confirmed` 字段错位；
2. 建立唯一 StrategySessionState 和问题账本；
3. 防止重复问题和阶段漂移；
4. 定义最低可用草案门槛和显式假设；
5. 返回可解释的草案阻断原因；
6. 统一 `companyId`、`socialAccountId` 和兼容 `accountId` 的语义；
7. 将增长打法、实验和策略决策版本传递到全部 ContentRun；
8. 统一所有创作入口到 ContentRun；
9. 发布记录增加平台内容 ID 和幂等防重；
10. 建立策略→内容→发布→反馈端到端回归测试；
11. 将不稳定高级能力移出 V1 默认主链；
12. 建立最小运行诊断面板，展示阶段、当前字段、问题、缺口和阻断原因。
13. 对热点采集 → 预览 → 人工入库 → ContentOpportunity → ContentRun → ContentTask 完成真实 Provider 和浏览器验收，证明热点库不是演示孤岛。

P0 验收后才进入真实账号小规模试运营。

### P1：内容实验闭环

1. OptimizationAction 适用范围和有效期；
2. accepted → running → supported/rejected 状态自动推进；
3. 按 RollingPlan/ExperimentPlan 定义真实周期；
4. 使用 Playbook 的 primarySignals 和 exitConditions；
5. 提升重复检测为语义和跨平台判断；
6. 启用并灰度真实爆款拆解与蓝图学习；
7. 完善标题、来源、蓝图和 Skill 多触点归因；
8. 建立用户表达偏好确认、撤销和版本。

优先级说明：热点真实链路验收属于 V1 已承诺能力，应在 P0 完成；真实爆款拆解和蓝图学习继续保留在 P1，待热点链路与至少一次真实人工发布反馈闭环完成后再启动。P1 启动前只维护 Work Item、合同和验收标准，不占用执行通道，也不得把演示规则蓝图描述为真实爆款学习。

### P2：策略反馈闭环与矩阵

1. 持久化 StrategyReviewCase；
2. 策略 Agent 接受、拒绝、追问和继续观察；
3. 策略候选与新 StrategyDocument 双向追溯；
4. 多账号独立运营；
5. 角色型矩阵和同题差异化；
6. 矩阵级复盘候选；
7. 用户确认后调整账号分工或增长打法。

### P3：平台自动化

1. 公众号草稿箱同步；
2. FlowSocial 定时任务、审批和失败重试；
3. 按官方真实权限校正公众号数据接口；
4. 小红书批量数据导入优化；
5. 在可靠授权可用时评估小红书平台连接；
6. 发布状态与平台内容 ID 自动同步。

### P4：生产化

1. 将大 JSON 状态拆分为正式业务表；
2. 引入事务、并发控制和迁移机制；
3. 登录、角色、权限和租户隔离；
4. 后台任务队列、调度、重试和告警；
5. 密钥托管与第三方授权；
6. 运行监控、审计日志和成本统计；
7. 清理或冻结旧 API、旧页面和过时文档。

## 16. 多线并行开发规则

### 16.1 主线职责

#### 总编排与黄金路径线

- 拥有状态机、对象关系、接口契约和端到端测试；
- 负责跨线字段对齐和 Feature Flag；
- 决定能力能否进入 stable 主链。

#### 策略 Agent 线

- 负责诊断、问题、建议、增长打法和策略质量；
- 不修改 ContentRun 和反馈内部结构；
- 通过 StrategyDocument 和 Adapter 对外通信。

#### 内容 Skills 线

- 负责单项能力和输出质量；
- 不修改策略快照、不启动其他 Skill；
- 遵守 Adapter、合同、失败策略和评测要求。

#### 平台与反馈线

- 负责发布记录、平台数据、指标和反馈状态；
- 不直接修改活动策略；
- 只生成战术行动或策略复核候选。

### 16.2 契约变更规则

任何跨模块合同修改必须：

1. 增加 schemaVersion 或提供向后兼容 Adapter；
2. 说明新增、废弃和默认字段；
3. 更新契约测试；
4. 更新一条端到端用例；
5. 不原地修改历史快照；
6. 提供数据迁移或只读兼容策略。

## 17. V1 端到端验收场景

### 场景 A：无经验用户从零起号

- 用户只有模糊想法；
- Agent 不重复提问；
- 用户可以接受候选建议；
- 以显式假设生成最低策略；
- 选择稳定垂直或热点桥接打法；
- 生成第一周计划和第一篇内容；
- 完成发布和基础复盘。

### 场景 B：知识资料驱动内容

- 用户上传产品和案例资料；
- 策略和内容只使用已确认或已授权事实；
- 缺少结果数据时不编造；
- 生成公众号和小红书差异化内容；
- 下载内容包并记录发布。

### 场景 C：受控热点冷启动

- 选择热点桥接打法；
- 系统只推荐 direct/bridge 热点；
- 保存实验比例、假设和退出条件；
- 发布后区分触达和目标受众信号；
- 单篇高表现不自动修改策略。

### 场景 D：内容优化实验

- 录入 72h/7d 数据；
- 生成相对账号基线的诊断；
- 用户采用只改变一个变量的建议；
- 建议进入下一批指定内容；
- 到期后标记支持、拒绝或样本不足。

## 19. 主要风险与控制措施

### 风险 1：继续堆功能导致主链失控

控制：P0 完成前，新能力默认只能进入 testing 或 experimental。

### 风险 2：为了快速上线绕过契约

控制：所有内容入口必须创建 ContentRun；所有长期策略变更必须产生新快照。

### 风险 3：LLM 重新承担状态管理

控制：阶段、字段、问题账本、readiness 和写入权限由确定性系统控制。

### 风险 4：版本很多但无法判断好坏

控制：每次 Skill/Playbook 修改必须关联失败案例、评测结果和灰度状态。

### 风险 5：反馈形成错误因果

控制：单篇只做观察；策略上行要求多周期、重复模式、业务结果和人工确认。

### 风险 6：新旧链路长期并存

控制：明确 stable 主入口；旧入口只读兼容或 deprecated，不再增加新功能。

## 20. 规划维护机制

### 20.1 决策记录

每次重要调整在本文档附录增加：

```text
日期
决策
原因
影响模块
是否修改合同
迁移方式
验收标准
回退方式
```

### 20.2 状态定义

- `planned`：只有规划，没有可执行代码；
- `scaffolded`：有数据结构或接口骨架；
- `implemented`：模块内部可运行；
- `integrated`：进入端到端主链；
- `tested`：有自动回归；
- `stable`：默认向 V1 用户开放；
- `production_ready`：经过真实平台、权限、并发和业务验证。

后续功能清单必须使用这些状态，不能仅以“文件已存在”判断完成。

### 20.3 完成定义

一项跨链功能只有同时满足以下条件才能标记完成：

- 产品入口存在；
- 服务端状态和数据持久化存在；
- 输入输出合同校验通过；
- 正常、失败、重试和回退路径明确；
- 至少一条集成测试；
- 归因和版本可追溯；
- 文档与 Feature Flag 已更新；
- 不依赖未启用的实验能力。
