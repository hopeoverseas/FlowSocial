# FlowSocial 协作与工作区规则

## 默认方式

跨电脑、IDE 环境安装、GitHub 最新 main 同步和共创后的文档收尾统一按[跨 IDE 共创指南](../../CONTRIBUTING.md)执行；本文补充任务分工和工作区细则。

FlowSocial 使用 Codex 原生任务协作与 Git，不维护第二套任务注册表、执行状态机或证据目录。
默认只有一个活动写入者，在当前附着分支和当前工作区中完成一个边界明确的任务。

每次开发遵循同一条短路径：

1. 按 CONTRIBUTING.md 核验 origin、同步最新 origin/main，并确认工作区干净后在任务分支开始；
2. 只读取任务直接相关的代码、合同和文档，不全仓扫描旧任务材料；
3. 完成边界明确的修改，运行与改动相关的最小充分测试；
4. 检查 diff，提交可独立理解的 commit；
5. 结束时再次确认工作区干净。

## Worktree 使用规则

默认不创建 worktree。只有以下情况之一成立时才使用临时 worktree：

- 两个真正独立的写任务需要同时进行；
- 高风险实验需要与当前开发隔离；
- 必须验证另一个分支且切换当前工作区会破坏正在进行的工作。

创建前必须确认目标分支、基准 commit 和写入边界。临时 worktree 不承载唯一副本的数据库、上传、
密钥或生成资产；任务集成或放弃后立即移除。未提交内容必须先提交、stash 或备份，禁止直接删除。

## Codex 协作

- 简单任务直接执行；复杂任务只维护一份短计划。
- 仅当子任务真正独立且并行能节省时间时使用 sub-agent。
- 同一文件或强耦合模块不安排多个写入者并行修改。
- 不要求为日常开发创建 Controller、Work Item、Execution、Registry 或重复审查记录。
- 交接只需说明：目标、改动文件、验证结果、已知风险和下一步。

## 验证与安全边界

验证证据以 Git diff、相关测试和必要的合同或迁移说明为准。涉及外部发布、真实账号、付费调用、
生产数据或不可逆操作时，仍需获得明确授权，并保留足以核对结果的回执。

产品中的人工确认门保持不变；治理简化不等于绕过内容选择、大纲确认、正文审批、视觉审批或发布授权。

## 历史与恢复

历史实现由 Git commits、branches 和 recovery tags 保存。仓库外备份仅用于恢复，不加入默认上下文，
也不在每次任务开始时扫描。长期有效的产品或架构结论应直接更新到固定文档。
